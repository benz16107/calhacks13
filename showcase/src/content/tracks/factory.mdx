## Why this needs an operating system

<Compare labels={["Droid on your own computer", "Droid on GurtOS"]}>
<div slot="a">

- It runs as you and can read every `.env` and token on disk.
- It can reach any host.
- It writes straight into your files.
- Its steps live in a terminal that scrolls away.
- Approvals are a prompt in a terminal, with no record you can search.

</div>
<div slot="b">

- Its own Linux user, with no sudo, in an overlay copy of the workspace.
- A firewall rule per task: only the hosts the task names.
- Undo removes one task's layer. Keep applies it.
- One append-only action log of every tool call, its result and its cost.
- The plan is an approval on your phone, and the box starts nothing until you approve.

</div>
</Compare>

The incident: in August 2025, malicious Nx packages started the AI CLIs already installed on developers' machines with permission-skipping flags and told them to search the disk for wallets, SSH keys, `.env` files and tokens. Sources: [Wiz, Aug 27, 2025](https://www.wiz.io/blog/s1ngularity-supply-chain-attack) (the AI CLI abuse and the flags) and the [Nx advisory](https://github.com/nrwl/nx/security/advisories/GHSA-cxm3-wv7p-598c) (the credentials posted to GitHub repositories). Wiz says the AI-driven activity succeeded in hundreds of cases, though the AI providers' guardrails sometimes blocked it.

## The live path, start to diff

This run was real Droid with Claude Sonnet 5.5, started on Oct 24 from the Factory app on a demo box. The fake bug is `add(a, b) = a - b` and the test wants 5 from `add(2, 3)`.

**1. Start.** The Factory app takes a job and a repository, shows your Factory plan's 5-hour and weekly use (read through the vault's key, which never leaves the core), and has two switches on: *Plan first* and *Coder and reviewer*. The same job can come from a GitHub issue labelled `droid`, a schedule, a webhook, a new file, an ASI:One chat, or `gurtos-exec`, a safe runner for `droid exec`.

## Droid's own pull request

<Details summary="Droid on a real GitHub repository">

Put `FACTORY_GITHUB_REPO` and `GITHUB_TOKEN` in the vault. Every 2 minutes the box checks the repo for open issues labelled `droid`. For each new one the core clones the repo into a workspace and starts a Droid task: plan first, medium autonomy, no network, and one tool, `factory.openPullRequest`. You approve the plan from the phone, the coder fixes the issue and the reviewer checks it. Droid then calls the tool, and the core copies the task's files, commits them to `droid/issue-<n>-<task>` and pushes with the token in a one-time header. Droid has no token and no route to GitHub. The test repository is [benz16107/gurtos-droid-demo](https://github.com/benz16107/calhacks13), kept for this track; the pull request was opened by a live `DEMO_LIVE=droid,github` run on the Vultr test box. It is not set up on every box.

</Details>

<Details summary="How the worker, the key swap and the hooks work">

`core/workers/droid.ts` is the worker inside every task: `createSession` (or `resumeSession` after a power cut), a box MCP server for tools and approvals, the permission and AskUser handlers, hooks and droids. Droid's calls to Factory go through the box's proxy, which swaps the placeholder key for the real one, so the real key never enters the task. A tool that needs a key runs in the box service through the task's broker socket and returns only a result.

Autonomy: `low` asks before anything but file edits and read-only commands, and the box takes away the network and makes every spend ask. `medium` also allows reversible commands, and caps the budget at $1. `high` runs without asking, on the task's own hosts and budget.

The hooks file sits in the task user's home, so a hijacked Droid could edit or delete it. The pause is a convenience for an honest agent. The security boundary is the OS: the task's own user, its copy of the files, its firewall rule, its budget and the vault.

</Details>

<Steps title="Try it" time="About 10 minutes on a test machine with the box installed and a Factory API key in the vault.">

1. Open the Factory app in the portal (`http://<box>:7700/`, then Factory under Apps), or run a job from a shell with a paired device's token:

   ```sh
   export GURTOS_BOX=http://<box>:7700 GURTOS_TOKEN=<a paired device's token>
   tracks/factory/gurtos-exec.ts --repo https://github.com/you/project.git --auto medium --plan --team \
     "Add a --json flag to the CLI and a test for it"
   ```

2. Approve the plan on the portal or your phone. Droid starts only after that.
3. Read the steps, the reviewer's verdict and the diff, then press Keep or Undo. Droid has no key and no route to GitHub; a pull request opens through the vault's token only if you set a repo.
4. Or run the merge gate with a real Droid: `./demo --live-droid` (about $0.50 of Factory credit).

</Steps>

<Limits title="What is not covered">

- **The hooks are a convenience.** The hooks file is in the task user's home, so a hijacked Droid could edit or delete it. The OS limits are the boundary.
- **The plan's wording is Claude's.** The portal and the iPhone notification show it as plain text, with markdown marks visible.
- **The Factory app mislabels a denied plan** as "The plan you approved".
- **The model provider sees what Droid sees.** Prompts, files and tool results go to Claude through Factory.
- **Droid's cost is a display.** The worker reports its own token counts, so a hijacked task could under-report them.
- **A shared kernel.** Tasks are Linux users, systemd units and overlay layers, not virtual machines.
- **The pull-request path** needs a GitHub token and repo in the vault. It ran live on one test box and is not set up on every box.
- **The plan's usage bars** read Factory's billing endpoint with the vault key, so they show nothing on a box with no Factory key.

</Limits>
