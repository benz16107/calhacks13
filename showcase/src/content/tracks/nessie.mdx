## How it works

<Flow steps={frontmatter.flow} />

**Live behavior, found while loading.** Where the live API and the spec disagree, the desk follows the live API:

- Create calls return the new object (`{"code": 201, ..., "objectCreated": {...}}`), where the spec says a string.
- Deposits drop cents: 2169.72 is stored as 2169. The seed rounds to whole dollars and keeps the exact amount in the
  description, and the tool tells the agent so.
- A bill created without `recurring_date` is stored, but then every bill list on its account fails with HTTP 400.
  Updating it does not fix it; only deleting it does. The seed always sets `recurring_date`.
- Account balances do not move when a completed deposit is added, so the desk reads deposits, not `balance`.
- Customers cannot be deleted, and transfers have no create route, so payments are deposits.

## Try it

On a test VM with `NESSIE_API_KEY` in the box vault, as root, from a copy of `tracks/credit-desk`:

```sh
sudo node sandbox/nessie-seed.ts cases/fogline-2026-10 /tmp/nessie-ids.json   # load (or re-check) the case
curl -s -X POST localhost:7700/t/credit-desk/run -d '{"case": "fogline-2026-10", "seats": ["clerk"]}'
```

A case gets the bank tool when its `case.json` says `"nessie": true`, meaning it was loaded with the seed script.

## Limits

- Read only: the desk does not write corrections or holds back to Nessie.
- Nessie keeps deposits in whole dollars, so exact amounts come from the deposit description.
- One key per sandbox: every test machine sharing the key sees the same Nessie data.
- Our questions for Capital One (is `recurring_date` meant to be required, can a customer be deleted, should a balance
  move on a deposit) are in `sandbox/nessie.md`.
