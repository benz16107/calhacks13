## Why it needs an operating system

On an ordinary computer, an agent that takes orders from a chat runs as you: it can read your keys, change any file and reach any host, and nothing can take back what it did. Agents that talk to strangers' agents make it worse, because any reply can carry a hidden instruction. GurtOS runs each chat request as its own Linux user, with its own copy of the files, no keys and only the network it was given. Spending over the task's budget waits for you, in the chat and on your phone, and Undo removes exactly that task's changes. The chat agent itself runs as an unprivileged user and uses only the box's HTTP API, the same one the portal and phone use, so it has no powers the portal lacks.

<Steps title="Try it" time="About 5 minutes at our table; needs an ASI:One account.">

1. Open the box screen's **ASI:One** window. It shows the agent's address and a pairing code, visible only there and on the owner's phone.
2. In [ASI:One](https://asi1.ai), find the agent by its address and open a chat.
3. Send `pair <code>` within 10 minutes, then "fix the failing test in my project".
4. Approve the card when it comes, then press **Undo** on the result and watch the box take that one task's changes out.

Without a pairing code, the agent only answers with the pairing step. Anyone can open [its public profile](https://agentverse.ai/agents/details/agent1qvuk46tnt9lnscher0pawl7pr5y525mak66ptwsrvg4kff0pfy9m2sy0us6/profile) signed out.

</Steps>

<Details summary="Run the agent on your own box">

1. Add `AGENTVERSE_API_KEY`, `ASI_ONE_API_KEY` and `FACTORY_API_KEY` (and optionally `APIFY_TOKEN`) as keys on the box.
2. Turn the agent on: `curl -X POST http://127.0.0.1:7700/t/fetch/agent -H 'content-type: application/json' -d '{"on": true}'`. The first time it installs uAgents, about 30 seconds. It stays on across restarts.
3. Open `http://127.0.0.1:7700/t/fetch/` for the address and the pairing code, then pair from ASI:One.

`DEMO_LIVE=fetch ./demo` runs the whole flow with a demo team on Agentverse: every mailbox, ASI:One's planner through its API, pairing, Fetch.ai's Weather Agent, the trap blocked, the box paying the oracle on Fetch's testnet after an OK, and the test buyer paying the Shopper. About five minutes. `DEMO_LIVE=fetch,droid` adds the Droid fix.

</Details>

<Details summary="How it talks to ASI:One">

**The planner.** ASI:One's planner sends the agent a message and uses its first reply, so the box replies within 40 seconds with the result, a card, or "still working" and the latest step. A later status check gets the task's next news and never starts a new task.

**Cards.** Approvals and results go out as `MetadataContent` in the Interactive Cards format, `card_kind: "review"`. A click comes back as JSON in a direct chat, or in the planner's own words; then it applies to the last card in that chat.

**The chat agent.** `agent.py` and `brain.py` run as the unprivileged user `nobody`. They can use the box's HTTP API but cannot read the keys or the workspaces. ASI:One's `asi1-mini` sorts each message (a status check or new work); a keyword rule takes over if ASI:One does not answer.

**Payments.** `fetch.pay` is a box tool. The wallet key stays in the core, and the core's one spending check decides: within the pay task's $0.25 budget it pays on its own, above it asks you in the chat and on your phone. It pays once per request, only an agent you asked, at most 5 FET.

</Details>

<Limits>

- No screenshot of the ASI:One chat page yet: the live runs went through ASI:One's API, which returns text and card data, not the page. The transcript above is from the messages the merge gate checks.
- A card click relayed through ASI:One's planner arrives without the selection, so it applies to the last card in that chat.
- The screening rules catch common shapes of an instruction. A novel one may get past the rules and the model check, but it still cannot make GurtOS do anything: replies are only ever relayed.
- All payments are test FET with no value. Fetch's Dorado explorer stopped indexing new blocks, so receipts link to the raw transaction on the testnet API.
- The three TEST agents are ours. They stand in for strangers so a hostile reply and payments both ways can be shown on cue.
- One team per box. To reply into a chat from a timer, `agent.py` sets a private uAgents field, so uAgents is pinned to 0.26.1.
