## Why GurtOS, and what each part is for

**The problem.** After a week of agents working, an ordinary OS cannot tell you what they did. The logs are scattered
across tools and files, and anyone with root can edit them, so the record is only as honest as the person who last
had root.

**GurtOS keeps one action log of every action, and Elastic keeps a copy the box cannot rewrite.** The Elastic agent
answers and investigates from that copy. It never acts on its own: pausing, undoing or stopping a task goes through
a GurtOS approval, so you still say yes. The Elastic keys stay in the root-only vault and no agent task ever sees them.
The box is light (one Node service, 4 GB of memory) and open source under Apache-2.0. Business is on main, and the person keys copy its roles by hand today.

## How it works

<Flow steps={frontmatter.flow} />

**Documents built for an agent.** Each document stands on its own, so no query needs a join. The task's title,
source, allowed hosts and budget are copied onto every one of its events, and `message` is one plain sentence, such as
`The box blocked "Job routine: apply to new postings" from reaching www.linkedin.com:443; it may reach only
boards.greenhouse.io`. The mapping is explicit (`dynamic: false`), and a unit test checks every field a document can
have is in it.

**Only real boxes and live demo runs.** An installed box (`BOX_HOME=/var/lib/box`) and a `DEMO_LIVE=elastic` run
ship their logs; dev boxes with their own `BOX_HOME` stay out. Each document's id starts with the machine's
`/etc/machine-id`, because two test VMs can share a hostname.

**Keeping up.** Serverless confirms a write only once it is durable, about 0.4 s per request, so one request per event
fell behind. In batches of up to 4 MB the reader keeps up with a whole demo run as it happens. If Elastic is down, it
retries every 5 s from where it stopped.

**The key stays in the core.** Only the `elastic.bulk` model job reads `ELASTIC_URL` and `ELASTIC_API_KEY`, inside the
box service. Tasks never see the key, and log readers have no vault access at all.

| Tool | Type | Answers |
|---|---|---|
| `box.changes` | ES-QL, `days`, `run` | Tasks done, undone or failed, with the files each done task changed |
| `box.costs_by_app` | ES-QL, `days`, `run` | Dollars per app: total, model, tools, number of tasks |
| `box.costs_by_task` | ES-QL, `days`, `run` | Dollars per task, with the paid tools it used |
| `box.failures` | ES-QL, `days`, `run` | Failed tasks and the error the box recorded |
| `box.task_timeline` | ES-QL, `task_id` | Everything one task did, in order. Used to explain a failure |
| `box.blocked` | ES-QL, `days`, `run` | Refused hosts, by task and app, with counts, times and allowed hosts |
| `box.search` | index search | Free text over the log, to find a task by a word |

`run` defaults to `installed`, the real boxes, so test runs never mix into an everyday answer. The agent's
instructions say which tool answers which question, that model spending is real Claude token prices while
tool spending is test money, and that a failed task's recorded error is often generic, so the cause comes from what
happened just before it.

## Try it

From the repo root, with `ELASTIC_URL`, `KIBANA_URL` and `ELASTIC_API_KEY` for your own Serverless project:

```sh
node tracks/elastic/agent.ts install                        # create or update the tools and the agent
node tracks/elastic/agent.ts ask "Why did the job routine fail? Look at demo run <run id>."
DEMO_LIVE=elastic ./demo                                     # ship a full run and ask all four questions
```

On a box, put the same three keys in `/etc/box/vault.env`. The track ships the box's whole log on its first boot and
then follows it live. In Kibana, open **Agents**, then **GurtOS log** (`/app/agent_builder/agents/gurtos-log`).

## Limits

- `tool.result` events carry no tool name, so the reader takes it from the `tool.call` just before. A restart between
  the two loses the name on that one result. The cost and the task stay right.
- The box records some failures only as "worker exited with N". The agent works around it from the timeline. Newer
  boxes add the worker's own last error line, which makes answers sharper.
- An entry can be changed in the seconds between the box writing it and Elastic receiving it. After that it cannot be changed without the check naming it. Root can still change the file on the box: what changes is that it is caught.
- A box that is fully taken over can stop sending, or lie about its own check. The agent flags a box that has gone silent, and `node tracks/elastic/agent.ts verify <log copy> <machine id>` checks a copy of a log without asking the box.
- The keys for people are issued by hand. A role change in GurtOS needs a new key.
- Only undo is requestable by Elastic today.
- The Elastic trial ends about Oct 30, 2026.
- Judges cannot open the Kibana project without a sign-in, so this page shows the answers as screenshots.
