## Why GurtOS, and what each part is for

**The problem.** A personal agent is only useful if it remembers you. Today that means uploading your life to someone's cloud, and any web page or photo an agent reads can try to plant false memories in it.

**GurtOS keeps the memory on a computer you own.** The index is in the box's own memory, each agent searches it through the box with no network and no keys, undoing a task takes its files out of the index, and the portal and phone show what every agent is doing. It runs on GurtOS Personal on your own laptop, even an old one (one Node service, no GPU needed for search), and is open source under Apache-2.0. What leaves the box today: a text copy in Moss's cloud index, which includes the descriptions a vision model wrote about your photos, and, when the Claude backup describes a photo, the photo itself goes to Anthropic. The local model is the default where Ollama runs; making Claude opt-in is being built.

## How it works

<Flow steps={frontmatter.flow} />

**What goes in.** Photos (`.jpg`, `.png`, `.webp`, `.gif`) by their description; text files up to 200 KB by path and
their first 2,000 characters; and every task when it finishes, fails or is undone, by title, state and Droid's final
message. It reads each workspace as it is now: the base files plus every finished task's changes. A file is read again
only when its size or time changes, and `docs.json` keeps every entry, so a restart rebuilds the index in
milliseconds without describing anything again.

**Which model describes.** One function sends the photo to any OpenAI-compatible chat API. The box tries models in
order and the first that answers wins; a model that fails is skipped for 5 minutes. The prompt asks for the kind of
thing first (a whiteboard, a receipt, a product), then details and readable text, then 8 keywords. Without that,
gemma4 called the whiteboard "a presentation slide".

**When Moss is out of reach.** If Moss cannot open at boot, search falls back to word matching and tries Moss again
every minute. Each result says which index answered.

**Agents use it safely.** A task lists `find.search` in its tools and calls it through its broker. It holds no Moss
key. Symlinks are skipped, so a task cannot point the index at the vault, and the file route serves only paths inside
a workspace.

```json
{ "query": "find the whiteboard photo", "kind": "photo", "topK": 3 }
```

## Try it

1. Put `MOSS_PROJECT_ID` and `MOSS_PROJECT_KEY` in the box's vault, `/etc/box/vault.env`. Photos are described by
   the first model in `MODELS` (`tracks/find/find.ts`) that answers: gemma4 in Ollama, then Vultr's hosted model, then
   Claude through Droid with the box's Factory key. Edit that list to keep photos on your own GPU.
2. Copy photos into any workspace. The track makes a `photos` workspace with the four test photos on first boot.
3. Search: `curl -s '127.0.0.1:7700/t/find/search?q=find+the+whiteboard+photo&kind=photo'`.
4. Or give a task the tool: `"tools": ["find.search"]`, and ask it to find something.

## Limits

- **Photos can leave the box.** When the local model is not available, Claude describes the photo in a Droid task, which sends it to Anthropic. Only text goes to Moss's cloud copy, and that text includes the descriptions. An opt-in for Claude is being built.
- **Vultr's vision model is untested.** The account needs a paid Serverless Inference subscription first.
- **Any task given `find.search` can search every workspace**, not only its own. A photo with text in it can carry
  that text into an agent's context as data.
- **Only the first 2,000 characters** of a text file are indexed. Long files need chunking.
- **Photos go to the model at full size.** Large phone photos are slower to describe.
- **A failed Claude description is not retried** until the box restarts, so a broken backup cannot start tasks in a
  loop.
