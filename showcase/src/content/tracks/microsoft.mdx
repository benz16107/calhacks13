## What a company needs before it says yes

<Compare labels={["An ordinary computer", "GurtOS Business"]}>
<div slot="a">

- The agent runs as its owner, with the owner's keys in files any process can read.
- Every agent shares one set of files, so a bad hour cannot be undone one task at a time.
- Nothing says who may approve what, so an agent can approve its own work.
- Stopping everything means finding and killing processes.
- The record is whatever the agent chose to write down.

</div>
<div slot="b">

- Each seat is its own Linux user with its own copy of the files. Keys stay in a root-only vault.
- Undo takes one task's layer out. Every other task keeps its own.
- Rules in plain words send each request to the one person who may answer it. Nobody answers their own request, and no agent approves an agent.
- One kill switch pauses every agent from an admin's phone or the computer's screen.
- An append-only action log, and an Audit view that is read-only for an auditor, with CSV export.

</div>
</Compare>

<Steps title="A one-week pilot" time="Day 0 setup, then a week in shadow. The plan is in docs/pilot.md.">

1. **Day 0, people and roles.** The admin adds each person with a role and a limit and pairs each phone, or signs people in with a work account (OpenID Connect, Microsoft Entra ID), taking each role from Entra groups.
2. **Day 0, the policy.** One rule per line, for example "Requests over $10,000 go to the Controller for approval." and "The Collections clerk goes live after 20 suggestions with 95% agreement." The rule tester answers "Who would approve this?" before the week starts.
3. **Days 1 to 5, shadow.** The seat works as usual, but each decision it would record becomes a suggestion that goes to a person through the same rules as any request. The box counts how often the person decides the same, and lists each disagreement.
4. **Day 5, the go-live check.** When the bar is met, the seat's row says Ready to go live. The admin checks every disagreement has an answer, then turns shadow off for that seat. The box never does this by itself, and the log records who did.
5. **Rollback.** One setting puts the seat back in shadow. The kill switch stops every agent at once. Both are in the log with the name of the person who used them.

</Steps>

## Responsible design, checked against Microsoft's six principles

Each control is mapped to Microsoft's Responsible AI Standard in `tracks/credit-desk/RESPONSIBLE.md`, with the code or test that shows it. This is a design mapping for a hackathon project with sandbox data, not an assessment against the Standard.

- **Fairness.** The seats never see protected attributes or the guarantor's name, SSN, date of birth or address. A test shows two applicants who differ only in those are byte-identical to the seats.
- **Reliability and safety.** Limits are enforced in code: no decision before the CRS checks, no payment to bank details changed by email without a confirming call, no duplicate payment. Runs are scored against a key, with precision beside recall.
- **Privacy and security.** Keys in a vault, a Linux user per seat, no network except through the desk's tools, test identities only.
- **Inclusiveness.** Plain letters, a neutral fraud-hold wording, anyone can bring their own case. Not done: translations and a screen-reader test.
- **Transparency.** Every decision carries rule ids, figures, CRS request ids and who approved it, and Ask why answers from the log months later.
- **Accountability.** A named person approves what the rules send them, the audit names who answered, and shadow mode needs a person to go live.

The merge gate runs the whole flow against a small provider of its own, with PKCE, signature, issuer, audience, expiry and nonce checks, and refuses someone in no mapped group. <Details summary="Measured impact per run, and the merge gate">

<Steps title="Try it" time="About 5 minutes on a box that has the credit desk's keys.">
