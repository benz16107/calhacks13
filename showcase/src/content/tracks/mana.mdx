## Also on main: guests and policy

Two more things Mana does on a GurtOS box, both gated by the owner. **Guest requests:** anyone can ask the box for a web lookup or a price check through Mana's public app, and nothing runs until the owner says yes on the phone or portal. Then the run happens in an empty workspace with no owner files, no network of its own, only the web tools and a 25 cent budget, at most 3 requests per guest and 10 in all per hour. **Rules drafted in Mana reach GurtOS Business:** a Mana chat drafts approval rules, the box turns them into a request showing what changes, and only after an owner or an admin says yes does the box apply them, only if it is that exact text. Both are covered by the track's merge-gate step.

## Evidence

### What Mana caught, and what the desk does now

| Mana caught | The desk now |
|---|---|
| Two customer records for one business (C-1007 and C-1011), each with a $10,000 limit: $20,000 of credit in two pieces, each inside the analyst's authority | Treats records that share an EIN, or a name plus an address, phone or email, as one business, and tests their combined balance against the lower limit (REL-1, SOD-5) |
| Application answers, emails and remittance notes are read by an AI agent, so a fraudster can write instructions into them | Treats text from applicants and customers as evidence, never an instruction. Text that tries to direct the desk is a fraud stop (GEN-3) |
| No defined fraud referral path | Stops every shipment on a fraud hold, cash in advance included, sends the controller every hit with its CRS request id, and never tells the applicant which check failed (FRR-1 to FRR-7) |
| Orders could stack past a limit, and uncleared checks could release them | Counts released orders and the new order in exposure, and counts only cleared payments (ORD-2, ORD-3) |
| No rules for disputes or early reviews | Stops dunning on a disputed amount but still counts it toward the limit; reviews risky accounts and limits above $25,000 every 6 months (DSP-1 to DSP-7, REV-2, REV-3) |

### The pushback, before adopting anything

The 69 proposals were checked against the test case first. Six problems went back to Mana: BND-5 would have moved
APP-1045 from band B to C; BIZ-3 needed to know who filed each UCC lien, and the business file only counts them;
HLD-1 quietly let the clerk release holds that ORD-1 reserves for the controller; GEN-2 would have treated "no file
at this bureau" as a failed check; FRD-7 would have flagged a customer's known second shop; LIM-3 and FRD-9 needed
data the case does not have. Mana fixed or deferred each one, cut the list to 35, and named six rules that could
still change an outcome depending on fields it had not seen. The third turn sent those fields; none of the six fire.

### Checked again in the repo

All 67 rule ids load with the desk's own loader, the draft's 32 rule texts are unchanged, and every rule id
mentioned inside a rule exists. None of the 35 changes a decision in the answer key.

### The rules in use

Under the 0.2 rules, live Droid runs cite the new rules: FRR-1 and FRR-2 on the fraud referral, REL-1 and SOD-5 on
the duplicate customer, COL-10 on the misapplied payment, COL-8 on the post-dated check, ORD-2 on order releases,
LIM-4 and TRM-1 on every credit decision. The latest of them, the full live run on Oct 24, caught 16 of 17 planted errors with 1 false alarm.

## How it works

<Flow steps={frontmatter.flow} />

**The GurtOS status app.** Mana's agent built it from a one-message spec, made it public, and tested it signed out at
phone size, with sample data and with a dropped connection. It runs in the viewer's browser and calls the box every
5 seconds. Until the box answers, it says "The box isn't reachable right now"; it never shows sample data.

It reads `GET /t/mana/status`, a route the Mana track adds to the box:

- **Public on purpose, so it holds little.** Task id, title, state, the latest step (cut to 160 characters), cost,
  source and time; the question and amount of each approval that is waiting; counts by state; the total cost.
- **Read-only.** One GET route. Approving still needs the portal or a paired phone.
- **CORS open** (`Access-Control-Allow-Origin: *`), so the Mana page can fetch it.

3. On your own box, the route is on by default: `curl -s localhost:7700/t/mana/status`. To show it to a Mana app,
   forward only that path through your web server, for example with Caddy:

```
handle /t/mana/status {
	reverse_proxy 127.0.0.1:7700
}
```

## Limits

- The status app is read-only by design. A judge watches tasks in Mana but approves on the portal or phone.
- The chat is a snapshot: Mana shares a chat as it was when it was shared.
- The project page was written before the OS was named GurtOS, so it says "the box".
