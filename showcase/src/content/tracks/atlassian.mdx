## Why this needs an operating system

On an ordinary computer an agent runs as a person, with that person's keys, on one shared set of files. So there is no record you can trust of what it did and why, nothing stopped it reaching what it should not, and no way to undo only the bad actions without undoing everyone's work. Jira can show the issue, but the issue is only as good as the system under it. GurtOS gives each task:

- **Its own copy of the files.** Each task is its own Linux user in its own copy-on-write layer. Roll back is taking that layer out, so it is exact and quick, and other tasks never notice.
- **No keys.** Keys stay in a root-only vault, so the agent has none to leak into an issue.
- **Only the hosts it needs.** The paste site is refused by the network rules, not by the model's good behavior.
- **An append-only log.** The Jira issue is written from that log, and agent output only enters as plain text, so a task cannot inject markup, links or mentions into Jira.

It runs on a computer you own: one Node service, 4 GB of memory and 17 GB of disk for GurtOS Server, no GPU, Apache-2.0. The Forge app is reusable: point `BOX_URL` at any GurtOS box.

<Details summary="How it works in depth">

<Flow steps={frontmatter.flow} />

**Into Jira.** The box feeds the track every event in its append-only log, in order, and saves its place, so it survives restarts and power cuts. Agent output only ever goes into Atlassian Document Format text nodes, so a task cannot inject markup, links or mentions into Jira. Status follows the task: queued is To Do, running is In Progress, waiting for an OK is In Review, and done, failed or rolled back is Done. It is safe to repeat: a crash between creating an issue and saving its key finds the issue by label instead of making a second one.

**Out of Jira.** The panel's resolver runs in Atlassian's cloud. It reads the issue's `box.task` property as the signed-in user, so the task id comes from Jira and never from the browser, asks Jira whether that user may edit the issue, and only then calls the box with the shared secret, passing the user's name for the log. The box checks the secret in constant time and checks that the approval belongs to that task. From the internet, the box forwards only its Jira routes and one read-only status route, and the rest of its API is a 404.

| Forge or Atlassian piece | Used for |
|---|---|
| `jira:issuePanel` (UI Kit, native render) | The agent task panel on `BOX` issues |
| `@forge/resolver` | `load`, `answer`, `rollback` |
| `jira:entityProperty` | JQL fields `boxState`, `boxCost`, `boxBlocked`, `boxPending`, `boxSource` |
| `api.asUser().requestJira` | Reads the property, the user's permissions and name, with the user's own access |
| `fetch` with `permissions.external.fetch.backend` | The one call out, to the box |
| Encrypted variable `BOX_SECRET` | The shared secret |
| Jira REST v3, from the box | `issue`, `properties`, `transitions`, `comment`, `search/jql` |

<Steps title="Try it" time="About 15 minutes with an Atlassian site and a GurtOS box.">

1. Put `ATLASSIAN_SITE`, `ATLASSIAN_EMAIL`, `ATLASSIAN_API_TOKEN` and `JIRA_BOX_SECRET` in the computer's key store (`/etc/box/vault.env`).
2. Turn syncing on: `echo '{"project":"BOX"}' > /var/lib/box/jira/config.json`.
3. Give the computer public HTTPS for `/t/jira/*` only. The README has the Caddy block.
4. From `tracks/jira/forge/`: `forge variables set --encrypt BOX_SECRET <secret>`, `forge deploy`, `forge install`.
5. Start any task on the computer. Its issue appears in `BOX`. Open the panel and try Approve and Roll back.

The full steps are in the [track README](https://github.com/benz16107/gurtos/tree/main/tracks/jira) and the docs guide [Connect Jira](https://gurtos.com/docs/guides/connect-jira/). The demo Jira site is not public, so we run it live at our table on Sunday.

</Steps>
