The test plays the phone through SpacetimeDB itself: it reads the rows with SQL over SpacetimeDB's HTTP API and
calls the `answer` reducer, which is what the phone's Approve button does. A task's own user cannot do the same: the firewall keeps task users away from port 3000, and moment
2 checks it ("it could not reach SpacetimeDB or the box's API to approve itself").

## How it works

<Flow steps={frontmatter.flow} />

**The module** (`core/spacetime/src/index.ts`, SpacetimeDB 2.13):

| Table or reducer | Who | What |
|---|---|---|
| `task` (public) | read by everyone | `id, title, state, source, workspace, worker, costCents, budgetCents, updatedAt, step, note` |
| `approval` (public) | read by everyone | `id, task, question, costCents, payee, purpose, state, by` |
| `owner` (private) | set at `init` | The identity that published the module. That is the box. |
| `putTask`, `putApproval` | the box only | Insert or update a row. Anyone else gets "only the box may do this". An answered approval never goes back to pending. |
| `answer({id, approved, by})` | anyone with the box's address | Sets a pending approval to approved or denied. A second answer does nothing. |

**The log stays the truth.** The action log on disk is fsynced line by line, and undo and resume are rebuilt from it.
SpacetimeDB is the live mirror: the box writes every task and approval change to it as it happens. If SpacetimeDB is
down, the box keeps working and catches up when it returns, and an answer given while the box was offline is applied
when its subscription reconnects. After a power cut, the box republishes the module and refills the tables from the
log, which is why the deploy in moment 4 is "still waiting for its OK, live in SpacetimeDB".

**Clients.** The portal is one Preact app for the box's kiosk screen, a laptop and a phone. It calls the HTTP API once,
then subscribes to both tables over `ws://<box>:3000`. A paired phone sends its device token with HTTP answers so the
log names it; through the reducer, `by` carries the screen's name. The Fetch.ai chat agent answers approvals whose ids
contain spaces through SpacetimeDB, as the phone does.

## Try it

On a box (Ubuntu 24.04 with `sudo core/install.sh`):

```ts
import { DbConnection } from './core/spacetime/bindings/index.ts';

DbConnection.builder()
  .withUri('ws://127.0.0.1:3000')
  .withDatabaseName('box')
  .onConnect((conn) => {
    conn.db.approval.onInsert((_ctx, a) => console.log('needs an OK:', a.question));
    conn.subscriptionBuilder().subscribeToAllTables();
    // conn.reducers.answer({ id: a.id, approved: true, by: 'my script' });
  })
  .build();
```

Then start a task that spends over its budget and watch the row arrive:

```sh
curl -s 127.0.0.1:7700/api/tasks -H 'content-type: application/json' -d '{"title": "Buy a GPU hour",
  "tools": ["example.spend"], "budgetCents": 500, "prompt": "Spend 8 dollars on a GPU hour with example.spend."}'
```

Or open the portal on two devices and approve on one.

## Limits

- **SpacetimeDB listens on every interface, and `answer` takes anyone's call.** Anyone who can reach port 3000 can
  answer an approval. Task users cannot. Keep the box on a network you trust, or block port 3000 at the firewall. A
  check of the device token inside the reducer is the next step.
- **`by` is free text through the reducer**, cut to 40 characters. Answers through the HTTP API with a device token
  name the paired phone reliably.
- **One database per box.** Two boxes show in one portal through each box's own SpacetimeDB, not a shared one.
- **Agents do not coordinate with each other here yet.** The shared state is between the box, its paused agents and
  the people who answer them.
