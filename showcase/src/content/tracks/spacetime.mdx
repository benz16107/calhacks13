GurtOS puts that picture in one self-hosted SpacetimeDB on each computer. ## Why it needs an operating system

An ordinary OS has no idea what an agent is. Two agents on one machine pick the same file, the person who must approve a payment finds out by polling, and the state lives in a mix of a database, a socket server and a cache, each with its own login. GurtOS runs each agent task as its own Linux user, so the OS knows exactly which task is asking. SpacetimeDB is where that knowledge becomes shared and live: the box names the task on every claim, vouches for each screen that may answer, and a task's own user is firewalled away from the database, so an agent can never approve itself.

<Steps title="See it on a box" time="About 20 minutes from a fresh Ubuntu 24.04 VM.">

1. Install: `sudo core/install.sh` from a checkout of the repo. It installs SpacetimeDB as `spacetimedb.service` and publishes the module.
2. Open the box screen and the **Live board** (turn it on in App Center if it is off).
3. Start a task that spends over its budget, and watch the request arrive on the Requests tab and on a paired phone:
   `curl -s 127.0.0.1:7700/api/tasks -H 'content-type: application/json' -d '{"title":"Buy a GPU hour","tools":["example.spend"],"budgetCents":500,"prompt":"Spend 8 dollars on a GPU hour with example.spend."}'`
4. Approve on one screen. The other clears at once, and the action log records who answered.

</Steps>

<Details summary="Subscribe from your own script">

```ts
import { DbConnection } from './core/spacetime/bindings/index.ts';

DbConnection.builder()
  .withUri('ws://127.0.0.1:3000')
  .withDatabaseName('box')
  .onConnect((conn) => {
    conn.db.approval.onInsert((_ctx, a) => console.log('needs you:', a.question));
    conn.subscriptionBuilder().subscribeToAllTables();
  })
  .build();
```

A connection the box did not vouch for can read the public tables but cannot answer: `answer` refuses it.

</Details>

<Details summary="How the module is built">

**The module** (`core/spacetime/src/index.ts`, SpacetimeDB 2.13, TypeScript) holds public `task`, `approval`, `job`, `agent`, `meter` and `activity` tables that the box's screens read, and private `person`, `request`, `routed_to`, `viewer`, `device` and `owner` tables that nobody reads directly.

- **Writes.** Only the box writes the mirror (`putTask`, `putApproval`), vouches for screens (`registerDevice`), and posts and claims jobs for a named task.
- **Answers.** A vouched connection calls `answer`. A pending row changes once: the first answer wins under the vouched name, and a later one is refused with "already approved by" and the name.
- **Visibility.** The `my_requests` view sends each connection only the requests routed to its person.

**The log stays the truth.** The action log on disk is fsynced line by line, and undo and resume are rebuilt from it. If SpacetimeDB is down, the box keeps working and catches up when it returns. After a power cut, the box republishes the module and refills the tables from the log, which is why the deploy in moment 4 is still waiting, live in SpacetimeDB.

**Who connects.** The box's own screen subscribes over `ws://127.0.0.1:3000`. A task never connects: it reaches the queue only through the broker tools, and the box calls the database for it. A phone or laptop elsewhere uses the token-checked API, and its Live board gets the same data every 2 seconds.

</Details>

<Limits>

- **Phones do not connect to SpacetimeDB.** SpacetimeDB listens on the box only. A phone uses the token-checked API, so its Live board refreshes every 2 seconds instead of on each change.
- **SpacetimeDB has no login of its own.** Anyone who could reach the port could read the public tables; only `answer` checks for a vouched connection. Exposing it on a network is opt-in, for a network you trust.
- **The Maincloud fleet view has been checked only by the demo's own test viewer.** The GurtOS phone app's Computers list reading it is not built or checked, and nobody else has read it yet. It reports counts only (tasks running, needing you, done and failed today, spent today, online), and each viewer is sent only the computers that granted them.
- **The credit desk's shared queue is opt-in and analysts only.** Its live run started two analyst agents, not the clerk or the payables seat, so it is not the scored headline run.
- **Open jobs and agent rows live only in SpacetimeDB.** After a schema reset they are gone; the action log still records every post, claim and result.
- **Reminders** nudge screens only, and restart their clock when the box refills a pending request after a reboot.

</Limits>
