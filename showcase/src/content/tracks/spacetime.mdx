## Why SpacetimeDB, and what each part is for

**The problem.** Live agent state usually needs a database, a websocket server, a cache and auth glue, which is heavy, fragile and breaks in the gaps between them. An ordinary operating system has nothing for it: agents on one machine collide, and the people responsible cannot see every request at once.

**GurtOS runs one self-hosted SpacetimeDB per box as the OS's live nervous system.** The box mirrors tasks and approvals into it, agents share work through it, people answer through it, and the rules about who may see and do what are enforced inside the database, in the same transaction as the change. It is one engine on the box, open source, and part of the GurtOS suite. For several machines, each box can publish a status summary to Maincloud: that part is written but not running yet. The action log on disk stays the record of truth.

The `track spacetime` step of the merge gate (32 passed in the last full run) adds the queue, the per-person requests, the double-answer refusal, the timer and the meter: 15 claims on 12 jobs gave 12 distinct jobs; a request routed to Rosa reached only Rosa's live client; a second answer was refused; a scheduled reducer brought Priya in after 3 seconds; and the meter matched the box's task list.

The moment-3 test plays the box screen through SpacetimeDB itself: it reads the rows with SQL over SpacetimeDB's HTTP API and
calls the `answer` reducer from an identity the box vouched for, then checks that an identity nobody vouched for is
refused. A task's own user cannot answer at all: SpacetimeDB listens on loopback, the firewall keeps task users away
from it, and moment 2 checks it ("it could not reach SpacetimeDB or the box's API to approve itself").

## How it works

<Flow steps={frontmatter.flow} />

**The module** (`core/spacetime/src/index.ts`, SpacetimeDB 2.13) holds the public `task`, `approval`, `job`, `agent`, `meter` and `activity` tables that the box's screens read, and private tables (`person`, `request`, `routed_to`, `viewer`, `device`, `owner`) that nobody reads directly. The `my_requests` view sends each connection only the requests routed to its person. The box alone writes the mirror (`putTask`, `putApproval`), vouches for screens (`registerDevice`), and posts and claims jobs for a named task. A vouched connection can `answer`: the first answer wins, recorded under the vouched name, and the later one is refused with "already approved by" and the name. `tracks/spacetime/README.md` has the full table.

**The log stays the truth.** The action log on disk is fsynced line by line, and undo and resume are rebuilt from it.
SpacetimeDB is the live mirror: the box writes every task and approval change to it as it happens. If SpacetimeDB is
down, the box keeps working and catches up when it returns, and an answer given while the box was offline is applied
when its subscription reconnects. After a power cut, the box republishes the module and refills the tables from the
log, which is why the deploy in moment 4 is "still waiting for its OK, live in SpacetimeDB".

**Clients.** The box's own screen calls the HTTP API once, then subscribes to the tables over `ws://127.0.0.1:3000`
and tells the box its identity so its answers count. A phone or laptop elsewhere never reaches SpacetimeDB: it sends
its paired token to the API, and the Live window shows it the same data every 2 seconds. Either way the answer lands in
the same row, so every screen agrees. A task never connects to SpacetimeDB at all: it reaches the queue only through the
broker tools, and the box calls the database for it.

## Try it

On a box (Ubuntu 24.04 with `sudo core/install.sh`):

```ts
import { DbConnection } from './core/spacetime/bindings/index.ts';

DbConnection.builder()
  .withUri('ws://127.0.0.1:3000')
  .withDatabaseName('box')
  .onConnect((conn) => {
    conn.db.approval.onInsert((_ctx, a) => console.log('needs an OK:', a.question));
    conn.subscriptionBuilder().subscribeToAllTables();
    // conn.reducers.answer({ id: a.id, approved: true, by: 'my script' });
  })
  .build();
```

Then start a task that spends over its budget and watch the row arrive:

```sh
curl -s 127.0.0.1:7700/api/tasks -H 'content-type: application/json' -d '{"title": "Buy a GPU hour",
  "tools": ["example.spend"], "budgetCents": 500, "prompt": "Spend 8 dollars on a GPU hour with example.spend."}'
```

Or open the box screen and a paired phone, and approve on one.

## Limits

- **SpacetimeDB has no login of its own.** It listens on loopback only, and `answer` accepts only vouched connections;
  anyone who could read the port could still read the public tables. Exposing it on a network (`STDB_LISTEN`) is opt-in,
  for a network you trust.
- **Phones do not connect to SpacetimeDB.** Only the box's own screens and local helpers do. A phone uses the
  token-checked API, and its Live window is refreshed every 2 seconds. Per-person visibility is enforced by the database
  for any connection that reaches it, and the public `approval` table, which the box's screens read, still holds every
  approval.
- **The module is republished at every boot** (and emptied if its schema changed), and the box refills tasks,
  approvals, people and the meter. Open jobs and agent rows live only in SpacetimeDB: after a reset they are gone, and
  the log still records every post, claim and result. Reminders restart their clock when the box refills a pending
  request.
- **The Maincloud fleet view is not running.** It is written, not published, and waits on one sign-in to SpacetimeDB.
- **The credit desk's use of the shared queue is opt-in and analysts only.** The live run (`runs/2026-10-24-coordinated-97ba92/`) started two analysts and not the clerk or the AP seat, so it is not the scored headline run. Fetch's team of box agents also posts to the queue, but only its posting and board are checked offline: its claiming agents need real Droid and have not been run live, so the claim is limited to a request that lists items becoming jobs on the shared queue.
- Each box keeps its own SpacetimeDB login, which fixed a bug where boxes sharing a VM broke each other's republish.
