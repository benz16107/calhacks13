**The public door stays narrow.** From the internet, on Oct 24:

| Request to the Vultr box | Answer |
|---|---|
| `GET /t/mana/status` | 200, the read-only status the Mana app shows |
| `GET /api/tasks` | 404 |
| `GET /api/health` | 404 |
| `GET /` | 404 |

The Jira routes refuse any call without the shared secret (401) and refuse an approval answered through another
task's issue; `./demo` checks both on every merge.

**The build outputs on the Vultr VM**, Oct 24:


The discs were then tested in QEMU: a blank disk install in about a minute, a healthy boot with every track
loaded, a power cut it came back from, an update to the second system slot, and a broken update that rolled
itself back after the 5-minute health check.

## How it works

<Flow steps={frontmatter.flow} title="How a judge's click reaches the Vultr box" />

The Vultr box is a normal GurtOS Server box. What makes it the public one is a single Caddy site in front of it:
Caddy gets a certificate, forwards the Jira routes and one read-only status route to the box's API on
`127.0.0.1:7700`, caps Jira request bodies at 64 KB, and answers 404 to everything else. The status route is public on
purpose and carries little: task titles, states, the latest step, cost, and the question of any approval that is
waiting. No prompts, tool calls, log lines or secrets.

The other Vultr jobs use the same VM over ssh from the build scripts:

- `./deploy vultr` installs exactly `origin/main` as the box service. It refuses a dirty or unpushed checkout.
- `./demo vultr` runs the merge gate in a throwaway box beside the installed one, with its own home, task users,
  ports and database.
- `image/build` ships the checkout to the VM and builds the discs there as root, from 40 named Ubuntu packages
  with mmdebstrap, then signs the update image.

## Try it

1. Deploy an Ubuntu 24.04 Cloud Compute instance on Vultr and give your ssh key root access.
2. Run the merge gate on it from a checkout of the repo: `BOX_SHELL='ssh root@<your instance>' ./demo`.
3. Install the box for real: copy the repo over and run `sudo core/install.sh`.
4. Build the discs on it: `BUILD_SHELL='ssh root@<your instance>' image/build`, then `image/build personal`.
5. To boot GurtOS itself on Vultr, follow
   [Install on a cloud instance](https://gurtos.com/get-started/install-server/#install-on-a-cloud-instance):
   serve the ISO, add it under Orchestration, ISOs, and deploy an instance from it.

## Limits

- One shared secret guards the Jira routes on the public box. Forge Remote's signed invocation tokens would let
  the box check each call came from the Forge app and that user.
- The Vultr box has no GPU, so /find describes photos with Claude in a sandboxed task instead of a local model,
  and Vultr's hosted vision model waits on a Serverless Inference subscription.
- No Vultr instance has booted the GurtOS disc yet; it is tested in QEMU only.
- The update key lives on the build VM. There is one key, with no rotation.
