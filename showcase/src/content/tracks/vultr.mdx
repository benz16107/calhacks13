## Evidence

**Booting the real disc on Vultr, Oct 24.** `tracks/vultr/up.ts` added the release disc (`gurtos-server-x86_64`, 1.5 GB) from a URL and created a `vc2-1c-1gb` instance that booted it. Times from creating the instance: running with an address 12 s, the installer copying the system at 50% after about 3 minutes, the installer finished and the GurtOS home screen up after about 5 minutes, and about a minute more for the box to come back from its own disk after the disc was detached, with the same name. The first attempt detached the disc after 300 s and cut the installer off, so the script now waits 480 s by default on one vCPU.

**Encrypted backups.** The box writes its state as a tar, pipes it through `age` to the owner's public key, and uploads it to a private Vultr Object Storage bucket; the owner makes the key pair on their own computer and keeps the private half, so Vultr holds only ciphertext and so does a thief of the bucket. Restoring onto a fresh Vultr instance took 2.8 s to download, decrypt and start the box on the restored folder. The finished task was listed as done, the waiting task as waiting, and after an OK on the restored box it finished and wrote its file. Not backed up: the vault, the relay identity and the box's CA key, which a restored box makes again.

**Firewall.** `PUT /t/vultr/firewall` makes a Vultr firewall group hold exactly the listed rules and puts the instance in it. It refuses a config with no ssh source or one wider than a /8, and it can never open 7700 or 3000. On a live instance, with ssh allowed only from a wrong address, ssh from outside timed out although the box's own firewall accepts port 22; putting the right address back let it in again.

## How it works

<Flow steps={frontmatter.flow} title="How a judge's click reaches the Vultr box" />

The Vultr box is a normal GurtOS Server box. What makes it the public one is a single Caddy site in front of it:
Caddy gets a certificate, forwards the Jira routes and one read-only status route to the box's API on
`127.0.0.1:7700`, caps Jira request bodies at 64 KB, and answers 404 to everything else. The status route is public on
purpose and carries little: task titles, states, the latest step, cost, and the question of any approval that is
waiting. No prompts, tool calls, log lines or secrets.

The other Vultr jobs use the same VM over ssh from the build scripts:

- `./deploy vultr` installs exactly `origin/main` as the box service. It refuses a dirty or unpushed checkout.
- `./demo vultr` runs the merge gate in a throwaway box beside the installed one, with its own home, task users,
  ports and database.
- `image/build` ships the checkout to the VM and builds the discs there as root, from 40 named Ubuntu packages
  with mmdebstrap, then signs the update image.

## Try it

1. Deploy an Ubuntu 24.04 Cloud Compute instance on Vultr and give your ssh key root access.
2. Run the merge gate on it from a checkout of the repo: `BOX_SHELL='ssh root@<your instance>' ./demo`.
3. Install the box for real: copy the repo over and run `sudo core/install.sh`.
4. Build the discs on it: `BUILD_SHELL='ssh root@<your instance>' image/build`, then `image/build personal`.
5. To boot GurtOS itself on Vultr, run `tracks/vultr/up.ts --iso-url <the disc's https address>` (it adds the disc, creates the instance, waits for the installer and detaches the disc), or follow
   [Install on a cloud instance](https://gurtos.com/get-started/install-server/#install-on-a-cloud-instance):
   serve the ISO, add it under Orchestration, ISOs, and deploy an instance from it.

## Limits

- One shared secret guards the Jira routes on the public box. Forge Remote's signed invocation tokens would let
  the box check each call came from the Forge app and that user.
- The Vultr box has no GPU, so /find describes photos with Claude in a sandboxed task instead of a local model.
- The first-boot wizard was shown on Vultr but not clicked through. The three live Vultr tests (disc, backup and restore, firewall) cost under $0.20 and their instances, disc and objects were destroyed afterwards.
- The release disc has no shell and does not ship the `age` program yet, so a restore on Vultr was run from the Server debug build of the same image.
- Vultr applies a firewall change on its own schedule: a removed rule took effect within 15 s, an added one took up to about 3 minutes.
- The update key lives on the build VM. There is one key, with no rotation.
