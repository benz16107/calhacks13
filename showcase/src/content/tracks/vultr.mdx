## Why it needs an operating system

Putting an agent on a rented server usually means one Linux user with every key in its environment and a port open to the internet. GurtOS changes what a cloud VM is for agents: each task is its own Linux user with its own copy of the files, keys stay where tasks cannot read them, each task reaches only the hosts it was given, and spending waits for the owner's phone. So the Vultr box can face the internet. Only the routes an app opens answer without a paired phone, and everything else is refused.

<Details summary="Run GurtOS on your own Vultr instance">

1. **The disc.** `tracks/vultr/up.ts --iso-url https://github.com/benz16107/gurtos/releases/download/v0.1.0-preview/gurtos-server-x86_64.iso` adds the disc to your account, creates the instance, waits for the installer and detaches the disc. Or by hand: Orchestration, ISOs, add by URL, then deploy from it ([the docs](https://gurtos.com/docs/get-started/install-server/#install-on-a-cloud-instance)).
2. **Or on Ubuntu.** Deploy Ubuntu 24.04, copy the repo over and run `sudo core/install.sh`.
3. **Backups.** Make an age key pair on your own computer, put the public half and an Object Storage key on the box, and turn backups on. Vultr only ever holds ciphertext.
4. **The merge gate.** From a checkout: `BOX_SHELL='ssh root@<your instance>' ./demo`.

</Details>

**Booting the real disc.** `tracks/vultr/up.ts` added the release disc (`gurtos-server-x86_64`, 1.37 GB) by URL and created a `vc2-1c-1gb`. From creating the instance: running with an address in 12 s, the installer at 50% after about 3 minutes, the home screen after about 5 minutes, and about a minute more to come back from its own disk once the disc was detached. The first attempt detached the disc after 300 s and cut the installer off, so the script now waits 480 s on one vCPU.

**Encrypted backup and restore.** The box writes its state as a tar, encrypts it with `age` to the owner's public key and uploads it to a private bucket. Restoring onto a fresh instance took 2.8 s to download, decrypt and start the box. The finished task stayed done, the waiting task came back waiting, and after an OK it finished and wrote its file. Not backed up: the keys file, the relay identity and the box's certificate authority key, which a restored box makes again.

**Firewall.** With ssh allowed only from a wrong address, ssh from outside timed out within 15 s although the box's own firewall accepts port 22; putting the right address back let it in. An added rule took up to about 3 minutes to apply.

**The public door, from outside:**

| Request to gurt-cloud.box.gurtos.com | Answer |
|---|---|
| `GET /t/mana/status` | 200, the read-only status the Mana app shows |
| `GET /t/wallet/sell` | 200, the x402 price list |
| `GET /t/wallet/sell/audit` | 402 Payment Required, $0.01 devnet USDC |
| `GET /api/tasks` | 401, pair this phone with this computer first |

**The mirror.** During judging, Vultr Object Storage served all four discs, `SHA256SUMS` and its signature, with the same checksums as the GitHub release. The mirror is off now; every file is on the [GitHub release](https://github.com/benz16107/gurtos/releases/tag/v0.1.0-preview).

</Evidence>

<Details summary="How the public box stays narrow">

The Vultr box is a normal GurtOS Server box. Its public address comes from GurtOS remote access: the box keeps an outbound tunnel to the relay, gets its own Let's Encrypt certificate and ends TLS itself, so the relay forwards encrypted traffic it cannot read. Each app lists the routes a stranger may call (`openRoutes`): Mana's status and guest requests, the x402 sell routes, Jira's routes (which also check a shared secret) and Apify's webhook. Every other path needs a paired phone's token.

The Jira routes refuse any call without the shared secret (401) and refuse an approval answered through another task's issue; `./demo` checks both on every merge. The status route carries task titles, states, the latest step, cost and the question of any waiting request. No prompts, tool calls, log lines or keys.

`./deploy vultr` installs exactly `origin/main` as the box service and refuses a dirty or unpushed checkout. `./demo vultr` runs the merge gate in a throwaway box beside the installed one, with its own home, task users, ports and database.

</Details>

<Limits>

- One shared secret guards the Jira routes. Forge Remote's signed tokens would let the box check each call came from the Forge app and that user.
- The Vultr box has no GPU, so photo descriptions for search use Claude in a sandboxed task instead of a local model. Vultr Serverless Inference was not used.
- The first-boot setup was shown on Vultr, not clicked through. The restore was run from the Server debug build of the same image, because the release disc tested that morning had no shell and no `age`. The final v0.1.0-preview discs ship `age`; the restore was not repeated on them.
- The box's own daily backup trigger and its firewall route were tested against stand-ins, not on a Vultr instance running the track.
- One Object Storage key can write every bucket on the account, including the mirror. The mirror's files are signed, so a swap shows, but a separate key is safer.
- The update key lives on the build VM. There is one key, with no rotation.

</Limits>
