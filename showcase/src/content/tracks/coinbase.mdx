## Summary

Coinbase asks for four parts: a summary, a working example, the architecture with its controls and limits, and builder feedback. This page follows that order.

**Who it is for.** People who leave agents running around the clock on a home machine or a cloud VM (GurtOS Server) and want them to buy what a job needs without handing over a card. And company agents that spend under company rules, where the action log is the audit trail (GurtOS Business).

**What it does.** Agents on the box pay for HTTP APIs that answer `402 Payment Required`. The box holds the wallet and a task only sees results. A payment within the task's budget goes through. One above it pauses the task until the owner approves on the portal or the phone, which shows the amount, the payee and the URL, while other tasks keep running. The box also earns: it sells three services over x402 and is listed in the Bazaar.

**Why it needs an operating system.** On an ordinary OS the agent runs as you, so it can read any key you have, reach any host, and spend with no record. GurtOS runs each task as its own Linux user with its own copy of the files and no keys, reaching only the hosts it was given. The key sits in a root-only file that only the box's payment tool opens. Budgets, the phone approval and the log are part of the OS, so every app on the box gets them, and Fetch.ai's payments use the same budget and approval path.

**Coinbase tools used.** The x402 v2 SDK (`@x402/fetch`, `@x402/core`, `@x402/svm` for Solana, `@x402/express` for the sellers), the CDP facilitator through `@coinbase/cdp-sdk/x402`, the x402 Bazaar (`listX402DiscoveryMerchant` and discovery search), the `upto` scheme, CDP Server Wallets with the policy engine, and Coinbase Onramp in sandbox mode.

<Steps title="Working example: x402 on the cloud box, now" time="One minute, no account.">

1. Open [the price list](https://gurt-cloud.box.gurtos.com/t/wallet/sell). It lists three services in devnet USDC, marked `"test": true`.
2. Ask for one without paying: `curl -i https://gurt-cloud.box.gurtos.com/t/wallet/sell/audit`. It answers `402 Payment Required` with a `payment-required` header: $0.01 on Solana devnet.
3. Try the box's private API: `curl -i https://gurt-cloud.box.gurtos.com/api/tasks`. It answers 401. Only the routes the wallet opens are public.

</Steps>

<Steps title="Working example: the whole flow on your own box" time="About 15 minutes with a CDP account.">

1. **Make a wallet** on a GurtOS box (a release disc, or Ubuntu 24.04 with `core/setup.sh`). This writes the key to the root-only file and prints the address:
   `node --experimental-strip-types tracks/wallet/keygen.ts | sudo sh -c 'cat >> /etc/box/vault.env; chmod 600 /etc/box/vault.env'`
2. **Fund it** at faucet.circle.com: USDC, Solana Devnet, 20 USDC. Payments need no SOL.
3. **Add CDP keys** for the facilitator: a Secret API Key from the CDP Portal as `CDP_API_KEY_ID` and `CDP_API_KEY_SECRET`. Without them it settles through x402.org.
4. **Run it:** `DEMO_LIVE=wallet ./demo` from a checkout of the repo. It pays, pauses for an OK, pays box to box, pays a metered search and checks everything on chain.
5. **Or reuse it outside GurtOS:** `curl -fsSL https://raw.githubusercontent.com/benz16107/calhacks13/main/tracks/wallet/install.sh | sh` installs the wallet as an MCP server and skill for Claude Code, with a budget and an approval prompt.

</Steps>

## Architecture, controls and limits

<Details summary="The seven controls">

- **The key stays in the core.** It is in `/etc/box/vault.env`, readable by root only. Only `wallet.pay` opens it, inside the box's own process. A task runs as its own Linux user and cannot read the file.
- **The CDP key stays with the seller.** Only the seller code reads it, and no box tool declares it, so no task can get it.
- **Budget, then the owner.** The core reserves each payment against the task's budget before the call runs. Above it, the task waits for an answer on the portal or phone. Denied means nothing is paid.
- **Exactly the agreed price.** If the API asks for anything other than the quoted amount, the wallet pays nothing.
- **Only devnet USDC.** It pays only the `exact` and `upto` schemes on Solana devnet in devnet USDC. The x402 client also refuses any single payment over $1.
- **Only the task's hosts.** The wallet reaches only hosts on the task's list, by the same rule as the task's network, and refuses redirects. A task cannot point it at the box's own API.
- **Never twice.** Before paying, the wallet writes a durable mark for that call. If the box loses power mid-payment, the resumed call refuses to pay again.

</Details>

<Limits title="Known limits">

- Devnet only, by design. Mainnet needs a different network and asset, real USDC and a review.
- The CDP Server Wallet lock was not run live: it needs a CDP Wallet Secret. Live runs keep the key in the box's root-only file. A CDP key that can manage policies could also loosen its own policy, so the policy key should be kept off the box.
- A metered payment counts at its cap in the task's cost until the core reads the settled amount.
- Bazaar free-text search did not find the box's routes on Oct 24; the lookup by pay-to address did.
- Onramp runs in sandbox mode only, and only the session step is verified (a $5 USDC quote on Solana, Oct 24). We did not open the checkout or complete an order, and the link points at the live pay.coinbase.com, so treat the button as a flow test. Onramp cannot deliver devnet USDC.
- After a power cut mid-payment, the call fails instead of checking the chain. The owner checks the wallet on Explorer.
- `GET` only: APIs that want a `POST` body are not supported yet. Responses are cut at 20 KB. The paid APIs in the demo are our own test sellers.

</Limits>

## Builder feedback

Kept while building, with times, in [FEEDBACK.md](https://github.com/benz16107/calhacks13/blob/main/tracks/wallet/FEEDBACK.md): 28 points across two rounds (x402 and the facilitator on Oct 23; Bazaar, `upto`, Server Wallets, policies, faucets and Onramp on Oct 24).

**What worked.** The first devnet payment settled on the first try, about 15 minutes in, about 1.5 s from the 402 to the 200. Swapping the x402.org facilitator for the CDP facilitator was one line. On Solana the facilitator pays the fee, so an agent wallet needs only USDC. `registerPolicy` was the right hook to pay only the approved offer.

**The friction that cost the most:**

1. Two Solana versions in one install: `@x402/svm` 2.28.0 pulls `@solana/*` 6.x while its token programs want `@solana/kit` 5. About 30 minutes to pin.
2. A payee without a USDC account fails with HTTP 402 and an empty body; the cause is only in a base64 header. About 20 minutes.
3. No idempotency key for payments, so a box that dies between settle and receipt would pay again on resume. We wrote our own durable mark.
4. Policies need a scope the default CDP key does not have, and that same scope lets a compromised server rewrite its own policy.
5. Bazaar gives almost no feedback: listing happens on the first paid call and nothing says so, and free-text search did not find a fresh listing that the merchant lookup did.
