## Why this needs an operating system

<Compare labels={["An ordinary computer", "GurtOS"]}>
<div slot="a">

Agents are built to read untrusted pages and install packages, and a fooled agent keeps all of your authority.

- It runs as you, so it can read `~/.aws`, `.env` files and every token on disk.
- Keys sit in the environment, where any process can read them.
- The network is open, so a stolen key can go anywhere.
- Nothing records what it did, and nothing undoes it.

</div>
<div slot="b">

Each task is its own Linux user, in its own copy of the files, with its own firewall rule. These are OS features, so they hold when the model does not.

- No key to read: the vault is root only, and the task holds a placeholder.
- One allowed host. Everything else is refused and logged.
- Approvals and the action log sit outside the task's reach, so it cannot approve itself.
- One task's changes are one layer. Undo removes it.

</div>
</Compare>

Armadin has not published judging criteria, so the page is built around the questions a security judge asks: what is the attack, what stops it, who tested it, and what is not stopped.

## The booby-trapped page, step by step

<Shot src="track/armadin/page-blocked.png" alt="A GurtOS task window for a task that read a page and then tried to reach attacker.example and a raw IP. A red notice says the task tried 2 things it is not allowed to do and both were blocked and logged. The steps from the action log show the blocked reach to attacker.example and to 1.1.1.1, with Undo task at the top." caption="The task window after the attack. The agent here is a scripted test agent that obeys the hidden instructions on purpose, so every block is checked on every run. The box refused both connections and wrote them in the log, and <strong>Undo task</strong> removes the task's files. Retaken Oct 24 from a demo box, test data only." />

| The hidden instruction | What stops it | What the log shows |
|---|---|---|
| Read the vault and every key | The vault is root only, and the task's environment and files hold none | The read fails with `EACCES` |
| Send them to attacker.example | The proxy allows only the task's own hosts | `net.blocked`, attacker.example |
| Go around the proxy to a raw IP | nftables lets the task's user reach only the proxy | `net.blocked`, 1.1.1.1:443 |
| Reach the box's API or SpacetimeDB to approve itself | The same firewall rule, and the API needs a paired device's token | Refused, directly and through an allowed host name |
| Look at other tasks or the box | The task sees no process but its own | No other pid is visible |

Then **real Claude**, running in Droid, reads the same page. In the Oct 24 run it refused the instructions, and the test searched its files, environment and logs for every vault value and found none. If a model obeys, the same controls still hold.

## A supply-chain attack, run for real

<Shot src="track/armadin/package-undone.png" alt="A GurtOS task window for the task Add a colour helper to the project. It is undone. A red notice says the task tried 6 things it is not allowed to do and all 6 were blocked and logged, listing the npm registry, the cloud metadata address, webhook.attacker.example and 1.1.1.1. The steps below show each blocked reach in red." caption="<code>gurt-chalk-utils</code> is a harmless imitation of the September 2025 npm worm, installed by a real <code>npm install</code> inside a task. It ran 11 steps; 6 were network reaches and every one was refused. The task ended <strong>Undone</strong> after it sent the decoy key out. Retaken Oct 24, test data only." />

The package reads environment variables and dotfiles, asks cloud metadata for credentials, tries to send them out, tries to publish to the registry, reads other tasks' files and tries to persist. Ten of the 11 steps are blocked or contained to the task's own copy; the other reads the environment, which holds only the box's two decoy cloud keys. The last step, a `curl` that sends the decoy cloud key, trips the tripwire: the box ends the task undone, with the package and everything it wrote gone.

<Details summary="Tripwire keys and the sandbox: what they cover and what they do not">

**Tripwire.** The box looks for the decoy key in a plain-HTTP request's address and headers, in a tunnel's host name, in tool-call inputs and in the log. It does not look in request bodies, inside tunnels or in the model relay, and it knows only the decoy, not a real secret. In the poisoned-package run the `curl` that sent the decoy tripped it. Node's `fetch` through a tunnel to an allowed host did not trip it, because the host allowlist blocked that request first.

**Sandbox.** The seccomp filter makes mounts, kernel modules, ptrace and perf, raw I/O, reboot, swap, the clock, keyrings and bpf fail with an error, and only the machine's own architecture runs. The merge gate checks the filter is active and the two-core cap is set. Not built: Landlock (the read-only system and write paths do that job) and a per-task disk quota.

</Details>

<Details summary="The hijacked payment">

A lookalike-sender email says "we changed banks, pay the new account", and a second honest bill is over the AP clerk's $5,000 limit. The bank change is refused in code before any person is asked, so it cannot wear a controller down. The over-limit bill pauses for the controller, who says no. </Details>

<Details summary="How each control works">

**The vault.** Keys live in `/etc/box/vault.env`, mode 0600, owned by root. The box refuses to start if anyone else can read it. A task asks its broker, a Unix socket only its own user can open, to run a tool by name. The tool runs in the box service with the keys it declared and returns a result. The result goes into the log, so tools never return a secret. Even the model key is never in the task: Droid holds a placeholder, and the box's proxy swaps in the real key on the way to Factory.

**The task.** A hardened systemd unit as its own user: `NoNewPrivileges`, `ProtectProc=invisible`, `PrivateTmp`, `ProtectSystem=strict`, `ProtectHome`, `PrivateDevices`, no capabilities, no SUID, no D-Bus, at most 2 GB of memory and 512 processes. It writes only into its overlay layer and its home.

**The network.** An nftables rule on task uids lets them reach nothing but the box's proxy. The proxy allows only the hosts in the task's spec (`example.com`, `example.com:8080`, `*.example.com`). A name that resolves to the box itself needs an exact host and port. Every refusal is a `net.blocked` event that reaches the portal, the phone, Jira and Elastic.

**Approvals.** A task cannot answer its own approval. The firewall keeps task users away from the box's API and SpacetimeDB, and the test tries both, directly and through its allowed host name.

</Details>

<Steps title="Try it" time="About 5 minutes on a test machine with the box installed.">


<Limits title="What GurtOS does not stop">

- **Root on the box gets everything.** The core runs as root and holds every key. A kernel exploit inside a task escapes users, systemd and overlayfs, which share one kernel. Tasks are not virtual machines.
- **A disk fill is not stopped.** There is no per-task disk quota.
- **Allowed hosts get whatever the task sends them.** If a task may reach a code host or a paste site, it can send it anything in its copy. Only the decoy key is looked for, and only in plain-HTTP requests.
- **Tools extend a task's reach.** A tool runs in the core, outside the task's network rule. A task allowed `apify.run` can have Apify fetch any URL. Give a task only the tools it needs.
- **Prompt injection is not prevented.** The model can still be fooled. GurtOS limits what a fooled agent can do.
- **The box's own screen needs no token.** Anyone with a shell on the box itself, or a stolen phone token, can still answer approvals. Revoke the phone in Settings.
- **Root can still change the log file on the box.** It is caught: each entry is chained to the one before, and when the box ships to Elastic, a create-only copy names any changed, removed or reordered entry. A change in the seconds before Elastic has the entry is not caught, and a fully taken-over box can stop sending or lie about its own check.
- **No disk encryption or verified boot.** Someone with the disk can read the vault.
- **No independent audit.** The scoreboard's attacks were chosen and run by the project.

</Limits>
