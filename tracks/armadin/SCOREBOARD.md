# Attack scoreboard

Forty-one OS-level attacks, each with an expected result, run against a real demo box on every merge
(`tracks/armadin/demo.ts` `attackScoreboard()`, and `attacks.ts` with its scripts in `attacks/`). Each one runs
as a task's own Linux user, inside its sandbox, the way a prompt-injected agent's commands would run. Six are
proved every merge by core's own `core/demo.ts` (moments 2 and 4); this table cites them rather than repeating the
work. Sources: the first sixteen rows from real runs on 2026-10-24 on the laptop VM (ARM64, no swap) and the
Vultr box (x86, 8 GB swap); the twenty-five rows from "The box's API over its own Unix socket" down are from the
launch red team's runs on 2026-10-29 on the x86_64 test VM (Ubuntu 24.04, 8 GB, no swap), each ending
`demo: 1 passed, 0 failed, 0 pending`.

**The gate.** A row expected caught that gets through fails the merge (a regression). A row published as not
covered that the core has since closed passes, tagged `FIXED` in the output, so this table can be moved without
the gate standing in the way of the fix. A row whose attack left no evidence fails too: the table never guesses.

Model-level attacks (can the model be talked out of refusing) are the Anthropic thread's
(`mcp:14377720-864a-4575-a780-fcf5de2c48e3`); this table is OS-level only.

## Notes for anyone extending this

- A destructive attack (fork bomb, memory hog, disk fill) gets its own task. A fork bomb's descendants outlive
  the `timeout` wrapper that starts them and keep eating the task's own `TasksMax` budget for the rest of its
  life, so a later command in the *same* task can starve. That is GurtOS containing the attack's blast radius to
  the one task that ran it, as designed; it just means a script must not ask that task to do anything else
  afterward.
- Read a task's own files directly from `${BOX_HOME}/tasks/<id>/upper` (not `root`): `sandbox.seal()` unmounts
  the overlay `root` mountpoint once a task ends, so a finished task's writes live only in `upper` from then on.
  This matters for a destructive attack especially, since its task is expected to end `failed`, and a `failed`
  task's writes never reach the merged workspace `view()`.
- The 2026-10-29 attacks live in `attacks.ts`, with the shell and Python they run in `attacks/`: one task runs
  `inside.sh`, a list of small probes, and each attack that needs its own state (a disk fill, a pair of tasks that
  talk, a forged question) gets its own task. Each script prints `<probe>: <result>` lines into the
  task's own copy, and `attacks.ts` reads them as root from the task's layer. Read a file a task wrote *before*
  undoing that task: Undo deletes the layer.
- Make the tasks that must overlap first (the listener and the sender): creating each task (a user, a copy) takes a
  moment on a busy machine, and a listener that waits a fixed time can miss a sender that started late.
- A script that may be killed by the fake worker's 20 s limit should print as it goes (`python3 -u`), or its output
  is lost with it.
- Keep attacks safe on a shared test VM: write only under the run's `BOX_HOME`, the task's own `/tmp`, or files
  named `armadin-<run>-*` in `/dev/shm` (removed at the end); take a host-wide lock only to let it go at once; never
  touch the installed box (`/var/lib/box`, port 7700).
- `/dev/tcp/<host>/<port>` and `:(){ :|:& };:` are bash-only; `/bin/sh` on this image is dash, which silently
  rejects both (an empty result, not an error) rather than running them. Use `nc` for raw connects and a POSIX
  function (`f(){ f & f & }; f`) for a fork bomb.
